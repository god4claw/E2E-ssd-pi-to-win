# §14. Риски и восстановление

<sub>[Главная](../../README.md) · [Часть 4](README.md) · [← §13](13-failures.md) · [§15. Периметр →](../5-hardening/15-perimeter.md)</sub>

Один раздел про то, что будет, когда что-то пойдёт не так. Здесь нет «рекомендаций»: только последствия и порядок действий.

| что случилось | последствие | что делать |
|---|---|---|
| Потеряны оба пароля `crypt` | **данные не восстановимы** | ничего. Только бумага, заранее |
| Умер SSD | данные потеряны | копия шифротекста ([§17](../5-hardening/17-backup.md)) |
| Потерян ключ SSH | доступ пропал, данные целы | новая пара, замена строки в `/etc/ssh/authorized_keys.d/cloud` |
| Украдена Pi вместе с SSD | чужие видят шифротекст и метаданные | ключ отзывается на Pi; если Pi нет — данные не прочтут, но и вы без диска |
| Pi сгорела, SSD цел | данные целы | прочитать диск на любой Linux-машине (ниже) |
| Удалён файл на `X:` | безвозвратно: корзины нет | копия или версии ([§18](../5-hardening/18-gaps.md)) |

## Потеря паролей `crypt`

Данные не восстанавливаются. Ни разработчиками rclone, ни перебором: пароль превращается в ключ через scrypt (дорогой по замыслу), содержимое закрыто XSalsa20-Poly1305.

Единственная защита — заранее записать **оба** значения: основной пароль и соль (`password2`) на бумагу, и хранить её отдельно от компьютера. Резервная копия шифротекста без паролей бесполезна ровно так же, как и без копии.

## Потеря ключа SSH

Не страшно. Создайте новую пару и замените строку:

```bash
sudo tee /etc/ssh/authorized_keys.d/cloud >/dev/null <<< 'restrict ssh-ed25519 AAAA...новая... cloud@win2'
```

Данные не затрагиваются: ключ отвечает за вход, не за расшифровку.

## Чтение вынутого SSD на другой машине

Штатный сценарий восстановления, если Pi вышла из строя. Подключите SSD к любому Linux и смонтируйте раздел:

```bash
sudo mkdir -p /mnt/ssd
sudo mount /dev/nvme0n1p1 /mnt/ssd
ls /mnt/ssd/data          # иероглифы — всё на месте, шифротекст цел
```

Дальше — crypt поверх локального пути, с теми же паролями и **теми же настройками имён**:

```bash
rclone config create local-data local
rclone config create recover crypt \
  remote=local-data:/mnt/ssd/data \
  filename_encryption=standard \
  directory_name_encryption=true \
  filename_encoding=base32768 \
  password=<пароль> password2=<соль> --obscure
```

> [!IMPORTANT]
> `--obscure` здесь нужен потому, что вы передаёте **открытые** пароли: rclone замаскирует их один раз. Если передать уже замаскированные значения и добавить `--obscure`, маскировка применится повторно, и ключ получится другим — данные окажутся нечитаемыми.

Проверка:

```bash
rclone ls recover: | head
rclone cat recover:путь/к/файлу | head -c 100
```

Если имена читаются, а содержимое — нет, значит пароль верный, а настройки шифрования имён нет (или наоборот). Сверьте `filename_encryption` и `filename_encoding` с исходным `rclone.conf`: это часть формата, а не вкусовая настройка.

## Кража Pi

Вор получает каталог нечитаемых имён и байты без структуры. Ему видны метаданные: сколько файлов, какого размера, когда менялись.

Ключ SSH при этом остаётся у вас и действителен ровно до тех пор, пока существует Pi. Если машина вернётся — смените строку в `authorized_keys`, чтобы старый ключ не принимался; если нет — данные целы, но доступа к ним нет, пока не восстановите SSD на другой машине.

## Восстановление из копии

Порядок, который стоит прогнать заранее, а не в момент аварии: [§17](../5-hardening/17-backup.md). Там же — учения: раз в квартал прочитать один файл из копии отдельной конфигурацией, собранной из бумажных паролей.
