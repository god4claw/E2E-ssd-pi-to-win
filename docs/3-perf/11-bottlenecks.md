# §11. Где узкое место

<sub>[Главная](../../README.md) · [Часть 3](README.md) · [← §10](10-measured.md) · [§12. Повседневная работа →](../4-ops/12-daily.md)</sub>

Из цифр [§10](10-measured.md) следуют четыре вывода. Первые три очевидны и полезны, четвёртый — про то, где обычно ошибаются с объяснением.

## 1. Шифрование бесплатно

Голый SSH даёт 103–113 МБ/с, с шифрованием rclone — 99–105 МиБ/с. Разница в пределах погрешности: узкое место — гигабитный кабель (теоретический потолок ≈ 118 МБ/с), а не криптография. Pi 5 успевает шифровать быстрее, чем сеть успевает нести.

Практический смысл: выбирать «менее стойкое, но быстрое» шифрование незачем, и наоборот — ужесточение настроек криптографии скорости не отнимет.

## 2. Диск быстрее сети вчетверо

430–460 МБ/с против ≈ 110. Апгрейд SSD бессмыслен: он простаивает. Апгрейд сети до 2.5 Гбит/с сразу даст рост — канал и есть потолок.

## 3. Мелкие файлы — слабое место

200 файлов/с при 64 КБ — это ≈ 12.8 МБ/с полезной скорости, в восемь раз хуже крупных файлов. Виновата не полоса, а число обменов: на каждый файл нужен отдельный набор запросов по SFTP, и восемь параллельных передач — это уже предел разумного.

Отсюда правило: архивы распаковывайте локально, а потом копируйте папку целиком с `--transfers 8`. Сто тысяч мелочи будут ползти независимо от того, что вы делаете с сетью.

## 4. Запись через диск: число честное, объяснение — нет

Измерено 65 МБ/с, и в первой редакции разбора это объяснялось «двойной записью»: файл сначала ложится в кэш на `C:`, потом уходит на Pi. Двойная запись действительно есть, но арифметика не сходится.

```
1 ГиБ = 1024 МБ
отправка на Pi при 104 МБ/с       ≈ 9.8 с
пауза --vfs-write-back 5s          = 5.0 с
итого                              ≈ 14.8 с  →  1024 / 14.8 ≈ 69 МБ/с
```

Получается ≈ 70 МБ/с — почти наблюдённые 65 без всякого учёта скорости кэша. То есть большую часть провала объясняет не полоса, а **пятисекундная пауза** после закрытия файла: rclone отдаёт файл, только когда к нему перестали обращаться. Для одного гигабайтного файла это 5 секунд простоя из 15.

Как проверить:

```powershell
rclone mount secret: X: --vfs-write-back 0s ...
Measure-Command { Copy-Item D:\big.bin X:\big.bin }          # до закрытия файла
# и отдельно — до появления файла на Pi:
while (-not (rclone lsf secret:big.bin)) { Start-Sleep -Milliseconds 200 }
```

Если с `--vfs-write-back 0s` запись через диск догоняет `rclone copyto` — узкое место в паузе, а не в двойной записи. Если не догоняет — смотреть на скорость кэша и антивирус.

Полезная формула на случай, если слагаемые всё-таки складываются (последовательная запись в кэш, затем передача):

```
1/v_X = 1/v_кэш + 1/v_сеть
```

При кэше 2 ГБ/с и сети 104 МБ/с это даёт ≈ 104 МБ/с, то есть двойная запись сама по себе почти ничего не стоит. Именно поэтому объяснять 65 МБ/с ею не стоит.

## Что действительно ускоряет

| что менять | эффект |
|---|---|
| Крупные файлы — `rclone copyto`/`copy` напрямую, а не через `X:` | до ≈ 105 МиБ/с, без паузы write-back |
| Сеть до 2.5 Гбит/с | потолок сдвигается с ≈ 110 к ≈ 280 МБ/с, пока диск не упрётся |
| Много мелких файлов — `--transfers 8` и копирование папкой | вдвое против одного потока (замерено) |
| Пачки мелочи — упаковать в архив | 12.8 МБ/с → ≈ 100 МБ/с |
| `dtparam=pciex1_gen=3` в `/boot/firmware/config.txt` | удвоит диск, но при гигабите вы этого не заметите |

Что **не** помогает: `--checkers` в команде `mount` (на VFS не влияет — [документация](https://rclone.org/commands/rclone_mount/)), апгрейд SSD, увеличение кэша сверх рабочего набора.

---

### Источники

- [`rclone mount`](https://rclone.org/commands/rclone_mount/): `--vfs-write-back`, влияние `--transfers` на VFS.
- Гигабитный Ethernet: 1 Гбит/с ≈ 118 МБ/с полезных.
- PCIe Gen 2 ×1 = 5 GT/s; Gen 3 ×1 = 8 GT/s.
