# §1. Pi: система и диск

<sub>[Главная](../../README.md) · [Часть 1](README.md) · [§2. Доступ по ключу →](02-ssh.md)</sub>

Диск на Pi — это обычный ext4. Вся защита живёт на клиенте, поэтому здесь не нужно ничего экзотического: ни LUKS, ни шифрованной ФС, ни RAID. Задача этого раздела — чтобы SSD был смонтирован по UUID, переживал перезагрузку без диска и не отъедал 5 % объёма под root.

## Что понадобится

| | |
|---|---|
| Одноплатник | Raspberry Pi 5 (Pi 4 тоже подойдёт, но там нет NVMe — будет USB, медленнее) |
| Питание | 5 В / 5 А; с NVMe-платой слабее блока питания — нестабильность под нагрузкой |
| Диск | M.2 2280 NVMe + плата-адаптер (HAT) |
| Система | microSD с Raspberry Pi OS 64-bit |
| Сеть | витая пара до роутера (Wi-Fi работает, но потолок падает втрое-впятеро) |

## Система и адрес

```bash
sudo apt update && sudo apt full-upgrade -y
sudo reboot
```

Закрепите за Pi постоянный адрес — резервированием по MAC в роутере или статикой в NetworkManager. Всё дальнейшее опирается на то, что адрес не меняется: он записан в `rclone.conf`, в `known_hosts` и в задании автозапуска.

## Диск

Убедитесь, что SSD виден, и **проверьте имя устройства** — ошибка здесь стирает не тот диск:

```bash
lsblk -o NAME,SIZE,TYPE,MODEL
```

Ожидаемо — `nvme0n1` нужного объёма. Дальше:

```bash
sudo parted -s /dev/nvme0n1 mklabel gpt
sudo parted -s -a optimal /dev/nvme0n1 mkpart cloud ext4 1MiB 100%
sudo mkfs.ext4 -m 0 -L cloud /dev/nvme0n1p1
```

`-m 0` снимает резерв под root. По умолчанию ext4 держит в запасе 5 % диска для системных нужд; на диске, где лежат только данные, это впустую отнятые ~47 ГБ от терабайта.

> [!NOTE]
> Имя раздела зависит от устройства: у NVMe и SD-карт это `nvme0n1p1` / `mmcblk0p1`, у USB-дисков — `sda1`. Проверяйте по `lsblk`, а не по памяти.

Постоянное монтирование — по UUID (имена вида `nvme0n1` могут переехать, UUID — нет):

```bash
sudo blkid /dev/nvme0n1p1          # запишите UUID
sudo mkdir -p /srv/cloud
echo 'UUID=<ВАШ-UUID> /srv/cloud ext4 defaults,noatime,nofail,x-systemd.device-timeout=10s 0 2' | sudo tee -a /etc/fstab
sudo mount -a
df -h /srv/cloud
```

| опция | зачем |
|---|---|
| `noatime` | Не записывать время последнего чтения: меньше лишних записей, дольше живёт SSD |
| `nofail` | Если диска нет, Pi всё равно загрузится и пустит по SSH |
| `x-systemd.device-timeout=10s` | Не ждать отсутствующий диск две минуты по умолчанию |

Без `nofail` отвалившийся SSD означает поездку за монитором и клавиатурой: система уйдёт в аварийный режим и не поднимет сеть.

**TRIM.** Не добавляйте опцию `discard` в `fstab`: онлайн-TRIM на дешёвых SSD даёт заметные подвисания. В Debian есть готовый `fstrim.timer`, который делает то же раз в неделю:

```bash
systemctl status fstrim.timer --no-pager
```

## Пользователь-хранитель

```bash
sudo adduser --system --group --home /srv/cloud --shell /usr/sbin/nologin cloud
sudo chown root:root /srv/cloud
sudo chmod 755 /srv/cloud
sudo mkdir -p /srv/cloud/data
sudo chown cloud:cloud /srv/cloud/data
sudo chmod 700 /srv/cloud/data
```

**Права здесь не косметика, а условие работы.** OpenSSH запирает пользователя в каталоге только если сам каталог и все его родители принадлежат root и не доступны на запись никому больше. Если сделать `/srv/cloud` принадлежащим `cloud`, вход просто перестанет работать — с невнятной ошибкой в журнале. Поэтому: внешняя папка root'овая, данные внутри — пользовательские.

Оболочка `nologin` означает, что этой учётной записью нельзя войти в систему — только работать с файлами. При этом `ForceCommand internal-sftp` (§2) всё равно перехватил бы любую попытку запустить команду.

## Проверка

| что | команда | ожидание |
|---|---|---|
| диск смонтирован | `findmnt -n /srv/cloud` | строка с `ext4` и `noatime` |
| метка и UUID на месте | `blkid /dev/nvme0n1p1` | `LABEL="cloud"` и `UUID=...` |
| права на каталог | `stat -c '%U:%G %a' /srv/cloud /srv/cloud/data` | `root:root 755` и `cloud:cloud 700` |
| запись от имени хранителя | `sudo -u cloud touch /srv/cloud/data/.probe && sudo -u cloud rm /srv/cloud/data/.probe` | без ошибок |
| переживает отсутствие диска | `sudo mount -a` после `umount` при выключенном SSD | загрузка не блокируется |
